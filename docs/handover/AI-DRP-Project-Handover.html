1. Project documentation

1.1 Project overview

The product is a bilingual (English and Telugu) web application that helps a consultant or entrepreneur produce a bank-ready Detailed Project Report. Users can match government and Andhra Pradesh MSME schemes, fill a scheme-specific form with optional AI assistance, preview a styled document, and download PDF, DOCX, or XLS.

The workspace is a two-package repository:

  • client/ — React 18 + TypeScript single-page app (Vite). Package name msme-dpr-client, version 1.0.0.
  • server/ — Node.js + Express + TypeScript API. Package name msme-dpr-server, version 1.0.0. MongoDB via Mongoose.

Primary user journeys on this branch:

  • Scheme Finder (/venture-match) ranks schemes with deterministic client-side rules, then hands the chosen scheme into a DPR.
  • Create New Latest DPR (/individual-dpr/create) builds a single-unit report. Each scheme has its own step list. A blank scheme is a vanilla bank term-loan pack of 18 steps.
  • Cluster DPR (/cluster-dpr/create) builds a multi-unit / SPV cluster report with generated narrative sections.
  • AI Guided Builder (/dpr/builder) and Chat (/chat) are separate assisted paths. Scheme Finder can also hand off into the guided builder.
  • Style and preview edits page size, type, colours, section order, and pictures for one DPR. The downloaded PDF is the document on screen.
  • Privacy account (/account/privacy) covers notice consent, AI on/off, data export, nominee, complaint, and account erasure.
  • Admin console (/admin, /admin/documents) covers analytics, users, DPR review, policies, audit, and RAG document upload.

1.2 Project objectives and scope

In scope on this branch

  • Account registration and login for adults (18+), with a privacy notice that must be scrolled and accepted.
  • Scheme eligibility matching for the catalog in client/src/lib/ventureMatch/schemes.ts (about 38 scheme codes, including PMEGP, MUDRA, CGTMSE, AP CMEP, PMEGP 2nd loan, short packs such as ZED and LEAN, and cluster routes such as MSE-CDP and SFURTI).
  • Draft, generate, preview, style, and download individual and cluster DPRs.
  • Optional AI fill, chat, translation to Telugu, quality scoring, and image generation, all gated by AI consent. Identity numbers are stripped before model calls.
  • English and Telugu interface copy (client/src/i18n/locales/en.json and te.json).
  • Admin review of users, DPRs, policies, and an append-only audit log.
  • In-app retention warnings and a purge job for idle DPRs and old audit rows.

Out of scope or not finished

  • A native mobile app, blockchain verification, and an API marketplace (listed as future ideas in the root README only).
  • Live, contracted integration with the AP MSME ONE portal. The client calls a configurable URL and falls back to mock scheme data when that call fails. Submission throws if the remote call fails.
  • Real email delivery. Outbound mail is a server log line. SMS is real only when Twilio environment variables are set.
  • DPDP Stage 4 (named grievance officer, real inbox, vendor contracts, breach playbook). Stages 1–3 are in code. docs/dpdp.md states this is not a compliance certificate.
  • Hosting design for the receiving organisation. See Part 4.

1.5 Frontend and backend overview

Frontend. client/src/main.tsx mounts App.tsx. Routes are listed in Part 2. State is Zustand (auth, individual DPR, theme, dev mode) plus localStorage for the auth persist key, Scheme Finder progress (venture-match-progress), and Scheme Finder handoff (venture-match-handoff). API access is client/src/lib/api.ts. Base URL is VITE_API_URL or http://localhost:5000/api. A short-lived in-memory cache (2–10 minutes) covers projects, DPRs, schemes, and profile. VITE_USE_MOCK_DATA=true switches the client to MockDataService. The consent gate loads the live profile and does not use that mock path.

Backend. server/src/index.ts is the long-running process used in development and the process that runs the retention timer. It requires OPENAI_API_KEY at boot. In production it also requires a strong JWT_SECRET and KYC_ENCRYPTION_KEY. server/api/index.ts is a second Express entry (serverless-style). It mounts the same routes but uses a default CORS origin of *, a 10 MB JSON limit instead of 50 MB, and it does not run the production secret checks, scheme seed, RBAC seed, assistant pre-warm, or retention interval. Prefer src/index.ts unless a host is explicitly wired to the serverless file.

1.6 Business logic and key workflows

Scheme Finder

Questions and option ids are fixed in lib/ventureMatch/questions.ts. evaluate() returns matches and exclusions. Each match has a dprRoute: full, short, cluster, cta, or none. Full and short routes open /individual-dpr/create?new=true&scheme=CODE. Cluster opens /cluster-dpr/create. CTA matches do not create a DPR. The individual form does not copy Scheme Finder answers into fields. It stores them for overlay rules (uploads, MUDRA bands, PMEGP education, and similar). Full rules: docs/venture-match-business-logic.md.

Individual DPR

Step counts come from schemeStepCatalog.ts. Vanilla is 18 steps. PMEGP is 14. MUDRA is 12. Short packs are shorter. Generate is allowed on the last visible step and stores scheme answers. Preview and PDF use one section per catalog step (question and answer), not the cluster chapter set. Quality scoring reads those stored answers. A super admin can save a scheme’s style as the default for the next DPR. Existing DPRs keep their own style. Full rules: docs/create-new-dpr-business-logic.md and styleeditor.md.

Fill this step (AI)

Documented in llm.md. Empty questions on the current step are batched: one model call for short and structured fields, and a second call only if the step has long write-ups. Earlier steps are reduced to a facts card (unit, district, location, products, rupee amounts in ₹ lakhs). The model must not invent a project cost. Each value is checked in code (numbers, dates 1990–2100, list shape, cost ceiling of five times amounts already on the card, long answers of at least 40 words). One failed field is retried once. Cluster “Generate suggestions” is a separate path: one call for the whole cluster step, with previous cluster steps included. The OpenAI Batch API is not used, because the user is waiting.

Privacy and retention

Notice version is 2026-09-4. Account consent is required. AI assist and analytics are optional flags. Idle DPRs (draft or submitted) are warned 15 days before delete and removed 12 months after the DPR’s last edit. The user account is not deleted by that job. Audit rows are removed 24 months after they were written. Account erasure is a separate, explicit action and does not wipe audit rows.

NotifyService (server/src/services/notify.service.ts) supports one kind today: retention_warning. It always writes an in-app UserNotification. The bell reads GET /api/privacy/notifications and mark-read POST /api/privacy/notifications/:id/read (id may be all).

  • Email: always mocked. The code comment marks SMTP as Stage 4. Privacy complaints are stored and a server log line is written. They are not emailed. Grievance address in the notice is privacy.grievance@msmeone.gov.in and is marked mock until Stage 4.

1.9 Analytics and tracking

There is no third-party product analytics SDK (no Google Analytics, Mixpanel, or similar) in the client dependencies.

Product analytics that do exist:

  • DPR quality record (DPRAnalytics collection, ml.service.ts): quality, completeness, bankability, satisfaction, funding outcome, sector benchmark comparison. Admin GET /api/admin/analytics aggregates these.
  • RAG metrics (RAGMetrics model) for document-assisted answers.
  • Audit events for security-relevant actions (login, consent, DPR create/change/download/delete, KYC, export, admin view). These are an audit trail, not a marketing tracker. Rows do not store Aadhaar or DPR body text.
  • Client navigation memory (lib/navHistory) so Back is named after the previous screen. It is local to the browser.
  • Consent flag privacy.analytics is stored on the user. Unlike AI assist, it is not wired as a hard server gate on the analytics routes. Treat “analytics off” as stored preference until that gate is added.

AI token use for fill-this-step is written to the server process log as llm.step (step, short or long, field count, input and output tokens). Those lines are operator logs. They are not shown in the UI.

1.10 Known issues and limitations

  1. Registration accepts a role from the client. POST /api/auth/register stores role when the body sends one, otherwise entrepreneur. The User enum allows admin and officer. The register screen sends the consultant mapping, but the API does not force that. A direct API call can request a privileged role. This should be fixed before a public production launch.
  2. Govt-official create restriction is a UI gate. canCreateDpr hides create actions for officer. Project and DPR routes only require a valid JWT. An officer token can still call create and generate.
  3. Copy still says enforcement is UI-only. English strings under rbac say “Enforcement is UI-only for now” and “Role updated in the UI”. Admin API routes do enforce the admin role. The strings overstate how open the API is, and understate the admin checks that already exist.
  4. Development accounts are seeded on boot if missing (see Part 4). They must not remain in a shared or production database.
  5. Two server entries behave differently (src/index.ts vs api/index.ts). The serverless entry skips production secret checks and the retention job.
  6. Email is not delivered. Complaints and retention email are log-only.
  7. AP MSME portal is not a reliable live integration. Failures return mock schemes or an error. Scheme rules used by Scheme Finder are the in-repo catalog, which can drift from a future portal API.
  8. README drift. Redis, Docker Compose, CDN, and “GDPR compliance” are not implemented as stated. Privacy work follows the DPDP plan in docs/dpdp.md, and Stage 4 is still organisational.
  9. /uploads is intentionally 404. Files are served only through authenticated file routes. Anything that still expects a public upload URL will fail.
  10. Large request bodies. JSON limit is 50 MB on the main server so HTML+CSS can be posted for PDF capture. That is a denial-of-service consideration if the process is exposed without a gateway limit.
  11. Dev mode skips required fields for super admins. It is off by default and not persisted, but it must stay unavailable to other roles (it already checks isSuperAdmin).

2. Architecture documentation

2.1 Overall system architecture

Browser SPA → HTTPS JSON API → MongoDB. The API also calls OpenAI, and optionally Hugging Face, Cloudinary, Twilio, and the AP MSME HTTP API. PDF generation runs inside the API process (Puppeteer/Chrome). There is no separate worker service and no message broker.

Static frontend hosting in this repo is described by vercel.json (build client, SPA rewrite to index.html). The API is a separate Node process. Content-Security-Policy in the API allows framing from localhost and from https://ai-dpr.up.railway.app, and frame sources include https://dpr-server.up.railway.app. Those hostnames are the only production URLs named in code. They are not an infrastructure specification.

2.2 Frontend architecture

  • Routing: React Router in App.tsx. Unknown paths redirect to /.
  • Auth gate: ProtectedRoute checks a token in Zustand or localStorage (token and persisted auth-storage). Missing token goes to /login. requiredRole is compared with toAppRole(). A mismatch goes to /dashboard. Children sit inside ConsentGate, which blocks until the current privacy notice is accepted.
  • State: Zustand stores. Server remains the source of truth for drafts after save.
  • i18n: English and Telugu. Scheme Finder has no language toggle on its own page; the rest of the app follows the UI language.
  • UI kit: Tailwind plus a small set of Radix primitives and shared layout (navbar, theme, accessibility bar, notification bell).

2.3 Backend architecture

Express application, routes mounted at /api from server/src/routes/index.ts. Layers:

  • Routes — auth, projects, dpr, schemes, feedback, admin, ai, apmsme, documents, privacy, plus GET /api/health.
  • Middleware — JWT authenticate, role authorize, AI consent, express-validator, central error handler.
  • Controllers — HTTP mapping.
  • Services — DPR generation, cluster DPR, OpenAI, quality/ML, financials, schemes, AP MSME, notifications, audit, retention, account erase, Cloudinary, translation, venture-match help, Whisper.
  • Models — Mongoose schemas.

On startup the main process connects to MongoDB, seeds four schemes if the collection is empty (PMEGP, MUDRA, CGTMSE, MSME-CDP), deletes any STANDUP scheme row, seeds RBAC test users if missing, pre-warms the OpenAI assistant cache, and schedules retention.

2.7 Data flow and application flow

  1. User registers or logs in. Server returns a JWT carrying userId, email, and role. Client stores it.
  2. If the notice version is not 2026-09-4, ConsentGate blocks the app until POST /api/auth/consent.
  3. Scheme Finder writes progress locally, evaluates in the browser, then saves a handoff object and navigates.
  4. Individual DPR loads the handoff for overlay rules only, then saves drafts with POST /api/dpr/cluster/draft/save. The URL gains projectId, dprId, and scheme.
  5. Optional AI calls send a reduced facts card. The server strips identity fields, calls OpenAI, validates the JSON, and returns suggestions. Failed checks stay blank for the user to type.
  6. Generate stores the report. Preview renders IndividualDPRDocumentView. PDF either posts captured HTML to the server or builds the Q&A document in individualDprDocument.ts.
  7. Downloads and staff views of another user’s DPR write audit rows.
  8. Every six hours the API process warns or deletes idle DPRs and old audit rows, and writes in-app notifications.

2.8 Authentication architecture

  • Passwords are hashed with bcrypt (cost 10) in a pre-save hook. The field is passwordHash. Minimum length 6.
  • JWT is verified in authenticate. Secret comes from getJwtSecret(). Production refuses a missing secret and refuses known dummy values (secret, your-secret-key, jwt-secret, and the dev fallback). Development may warn and use a local dummy secret.
  • Logout is an audit event. Tokens are not stored server-side, so logout does not revoke a token before it expires. Expiry is whatever signToken sets in the auth controller.
  • AI routes use requireAiConsent. A false aiAssist flag returns 403 with code AI_CONSENT_REQUIRED. Draft save and downloads stay available.

2.9 Integration architecture

Outbound calls are synchronous HTTP from the request that needs them (OpenAI, AP MSME, Twilio, Cloudinary, Hugging Face). RAG upload attaches files to the OpenAI vector store id in MAIN_VECTOR_STORE_ID. If that variable is empty, some code paths fall through to a placeholder. Set a real store id before relying on RAG.

KYC and cluster photos stay on the API disk (optionally AES-256-GCM with KYC_ENCRYPTION_KEY). They are read back only through GET /api/dpr/cluster/files/:fileId.

2.10 Background jobs

One in-process job exists. runRetentionJob() starts about 20 seconds after listen, then every 6 hours, via setInterval in server/src/index.ts. An admin can also run it with POST /api/admin/retention/run.

There is no queue (no Bull, SQS, or cron daemon in the repo). The serverless entry does not start this timer. If more than one API instance runs src/index.ts, each instance will run the job. The job is written to be safe to repeat, but overlapping instances should still be treated as an operations choice, not as a designed worker fleet.

Assistant cache pre-warm at boot is a one-shot OpenAI call, not a scheduled job.

2.11 Error handling and logging architecture

Users see a short JSON message, not a log and not a stack trace, except when NODE_ENV is exactly development. In that mode the error handler also adds stack to the JSON. Production responses stay { success: false, message }.

Operator logs stay on the server process:

  • Morgan writes HTTP access lines to stdout (dev format).
  • The error handler writes the error to stderr.
  • Retention, SMS, and email helpers write their own stdout lines for operators.
  • The UI uses toast text for success and failure. It does not render server logs.

Validation errors from express-validator return 400 with field messages. Unknown routes return 404 Route … not found. Rate limiting returns a plain “too many requests” message. AI consent and under-18 refusals use stable code values (AI_CONSENT_REQUIRED, UNDER_18) so the client can show the right sentence.

2.12 Security architecture

  • Transport and headers: Helmet, including a CSP that allows the app to frame its own PDF preview. CORS origin is CORS_ORIGIN or http://localhost:5173 on the main server. Credentials are allowed. The serverless entry defaults CORS to *, which should not be used for a credentialed production API.
  • AuthZ: authorize(...roles) plus roleAllowed. Admin routes and document mutations require admin. Scheme-style save requires admin. File reads allow the owner or admin/officer. Staff opening another user’s DPR writes admin_view.
  • Privacy of model calls: sanitizeForAi drops Aadhaar, PAN, passbook, UPI, and file-URL keys and redacts those patterns inside strings, including Cloudinary and /uploads URLs.
  • Files at rest: production refuses to boot without KYC_ENCRYPTION_KEY. The key is a server secret hashed into AES-256-GCM. It is not per user. Dev may omit it; files are then private by route but plaintext on disk.
  • Public uploads: /uploads always 404.
  • Audit: append-only events with time, user id, role, action, optional target, and IP. Users can read their own activity. Admins can filter and export CSV.
  • Age: registration and DPR save/generate refuse an applicant under 18.
  • Gaps already listed in 1.10: self-selected role on register, officer write access via API, non-revocable JWT, 50 MB body limit, seeded test users.

2.13 Performance and scalability architecture

  • Response compression is on.
  • MongoDB pool is capped at 10 sockets. Timeouts are raised for cross-region hosts (comments mention Railway and Atlas).
  • The client caches a few GET responses in memory for a few minutes.
  • Fill-this-step was changed from one model call per question to at most two calls per step, specifically to cut wait time and token repeat. See llm.md.
  • PDF capture and Puppeteer run on the API machine. That is the scaling limit for concurrent downloads. There is no horizontal worker split.
  • Rate limit is in-memory (express-rate-limit default). It does not coordinate across multiple instances.
  • No CDN, Redis, or read-replica configuration is in the repo. The README lines that mention them are not implemented.

3.2 Role-based access control

Two layers exist, and they are not the same.

  • API. Most business routes require any valid JWT. Admin console and document-admin routes require stored role admin. Scheme default style save requires admin. Cluster file read and “view someone else’s DPR” treat admin and officer as staff.
  • UI. /admin and /admin/documents require Super Admin. canCreateDpr is true for Consultant and Super Admin only, so Govt Official does not see create actions. Dev mode is Super Admin only. An Access Control tab on the admin dashboard previews the three roles. Its own hint text says enforcement is still UI-oriented.

3.3 User permissions

Consultant (stored entrepreneur), as implemented for a normal signed-in user:

  • Create and edit own projects and DPRs, save drafts, generate, download PDF / DOCX / XLS.
  • Use Scheme Finder, guided builder, and chat.
  • Use AI features only after opting in. Typing, saving, and download still work with AI off.
  • Style the current DPR. Cannot save a scheme-wide default style.
  • View own quality information, profile, privacy export, activity, and notifications.
  • Cannot open the admin console or upload the RAG knowledge base.

3.4 Admin permissions

Stored role admin (UI Super Admin), via /api/admin and the admin pages:

  • Platform analytics.
  • List users and update them, including role. An admin cannot change their own role.
  • Delete a user. Deletion uses the same eraseAccount() path as self-service erasure.
  • List projects, feedback, and DPRs. Approve or reject a DPR.
  • Create, edit, delete, and approve policy records.
  • Read and CSV-export the audit log. Run retention immediately.
  • Upload, list, and delete RAG documents and manage vector stores.
  • Save a scheme document style as the default for future DPRs.
  • Open another user’s DPR (audited as admin_view) and read KYC/cluster files.
  • Use dev mode on create-DPR screens.

3.7 Authentication and authorization

Authentication is email + password, then JWT. Authorization is the role checks in section 3.2 plus ownership checks in DPR and file controllers (staff bypass for admin and officer). There is no per-permission table, no OAuth, no SSO, and no multi-factor authentication.

3.8 User management

  • Self-service: register, login, edit profile, privacy settings, delete own account.
  • Admin: user list (paged, filterable by role), edit name, email, role, location, phone, Udyam number, and delete.
  • Role changes persist through PUT /api/admin/users/:id. The success toast text still says “Role updated in the UI”, which is misleading. The admin call is a real write.
  • There is no invite email and no password-reset endpoint in the auth routes.

3.9 Access restrictions

  • Under 18 cannot register or be the named applicant on a DPR.
  • Account consent and the current notice version are required to pass the app gate.
  • AI features refuse when aiAssist is false.
  • Non-admins receive 403 on /api/admin and on document admin routes.
  • KYC bytes are not on a public URL and are not sent to the model.
  • Users see only their own privacy activity and notifications.

3.10 Permission workflows

  1. New consultant. Register as Consultant. Scroll and accept the notice. Optionally enable AI. Land on the dashboard.
  2. Promote to admin or officer. An existing admin edits the user on the User Management tab. The stored value must be admin, officer, or entrepreneur. The UI maps the three labels before sending.
  3. Review. Admin opens DPR Management and approves or rejects. Officer is described as a reviewer in the UI copy. The approve/reject routes themselves are under the admin router, so they require stored role admin, not officer.
  4. Withdraw AI. User turns AI off under privacy settings. Later AI calls return 403 until they opt in again.
  5. Erase. User confirms DELETE, or an admin deletes the user. Mongo rows for that user’s projects, DPRs, files, and related records are removed. Audit rows stay until the 24-month clock.

4.6 Database and production configuration

  • Use a dedicated database per environment. The app does not prefix collection names.
  • Take a backup before the first boot against a database you care about. Boot deletes every Scheme document with code STANDUP and inserts the four seed schemes when the collection is empty.
  • Retention defaults: DPR idle 365 days, warning 15 days before, audit 730 days. Override only with explicit integers.
  • Losing KYC_ENCRYPTION_KEY makes existing encrypted files unreadable. Store it with the same care as the database.
